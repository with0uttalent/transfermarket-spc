# Лекция: DNS с уклоном в DevSecOps

Полный самодостаточный материал по DNS: как устроено, все ключевые типы записей,
кеширование, и — главное для тебя — **безопасность**: атаки на DNS и защита,
сертификаты, subdomain takeover, DNS в Kubernetes. Примеры привязаны к твоему
стенду (`gost-machine`, где nginx проксирует два приложения по `server_name`).

Как учить: читай раздел → сразу выполняй команды из него на своём сервере →
отвечай на вопросы в конце. Всё, что нужно из инструментов — `dig` (пакет
`dnsutils`/`bind-utils`).

---

## 1. Зачем DNS вообще существует

Компьютеры маршрутизируют пакеты по IP-адресам (`192.0.2.10`), а люди помнят
имена (`transfermarket.example.com`). DNS — это распределённая база «имя → адрес»
(и не только адрес). Ключевое слово — **распределённая**: нет одного сервера,
который знает всё. Ответственность делегирована по уровням, и это одновременно
источник масштабируемости и источник почти всех уязвимостей.

Аналогия: DNS — это система указателей. Корень знает, кто отвечает за `.com`;
`.com` знает, кто отвечает за `example.com`; `example.com` знает конкретный IP
`transfermarket.example.com`. Каждый уровень знает только «куда спросить дальше».

## 2. Иерархия и роли

```
                     . (корень)
                     │  знает делегирование всех TLD
        ┌────────────┼─────────────┐
       .com         .org          .ru        ← TLD (Top-Level Domain)
        │
   example.com                                ← домен 2-го уровня (ты его купил)
        │  здесь живёт твоя ЗОНА
   ┌────┴─────────────┐
 transfermarket     quake             ← поддомены / записи в зоне
```

Действующие лица:

- **Root-серверы** (13 логических: `a.root-servers.net` … `m`, физически —
  сотни машин по anycast). Знают, какие NS отвечают за каждый TLD.
- **TLD-серверы** (`.com`, `.ru`, …) — знают NS-серверы доменов внутри своей зоны.
- **Authoritative (авторитативный) сервер** — конечная инстанция для *твоей* зоны.
  Это тот сервер, где ты добавлял A-запись. Он «истина» для `example.com`.
- **Recursive resolver (рекурсивный резолвер)** — тот, кого спрашивает клиент. Он
  сам обходит иерархию (root → TLD → authoritative) и возвращает готовый ответ.
  Примеры: резолвер провайдера, `8.8.8.8` (Google), `1.1.1.1` (Cloudflare).
- **Stub resolver** — крошечный клиент в твоей ОС (то, что настроено в
  `/etc/resolv.conf`). Он не обходит иерархию сам — просто спрашивает рекурсивный
  резолвер и верит ответу.

**Recursive vs iterative — важное различие:**
- Клиент делает **рекурсивный** запрос резолверу: «дай финальный ответ, мне всё
  равно как».
- Резолвер делает **итеративные** запросы вверх по иерархии: root отвечает «иди
  к TLD», TLD отвечает «иди к authoritative», authoritative даёт адрес.

```bash
# посмотреть весь путь обхода своими глазами (минуя кеши):
dig +trace transfermarket.example.com
```

## 3. Зона, делегирование, glue-записи

- **Зона** — это участок пространства имён, за который отвечает один набор
  авторитативных серверов. `example.com` — зона; внутри неё записи `www`,
  `transfermarket`, `quake`.
- **Делегирование** — когда TLD говорит «за `example.com` отвечают вот эти NS».
  Делается NS-записями в родительской зоне.
- **Glue (склеивающая запись)** — если NS домена находится *внутри самого домена*
  (`ns1.example.com` обслуживает `example.com`), возникает курица-яйцо: чтобы
  узнать IP `ns1.example.com`, надо спросить `example.com`, но чтобы спросить его —
  нужен IP `ns1`. Родительская зона решает это, отдавая IP NS-сервера напрямую
  (glue) вместе с делегированием.

**DevSecOps-нюанс:** ошибки делегирования (NS указывает на сервер, который больше
не обслуживает зону — «lame delegation») — частая причина «сайт то работает, то
нет»: часть резолверов попадает на живой NS, часть на мёртвый.

## 4. Типы записей (records) — что должен знать инженер

| Тип | Назначение | DevSecOps-значимость |
|-----|-----------|----------------------|
| **A** | имя → IPv4 | базовая; dangling A → takeover |
| **AAAA** | имя → IPv6 | часто забывают → «IPv6 работает мимо firewall» |
| **CNAME** | псевдоним: имя → другое имя | главный источник **subdomain takeover** |
| **NS** | какие серверы авторитативны для зоны | делегирование; ошибки = lame delegation |
| **SOA** | «паспорт» зоны: серийник, TTL негативного кеша | negative caching, зонные трансферы |
| **MX** | почтовые серверы домена | цель спуфинга; связка с SPF/DKIM/DMARC |
| **TXT** | произвольный текст | SPF, DKIM, DMARC, ACME-челленджи, верификация |
| **CAA** | какие удостоверяющие центры могут выпускать сертификаты | защита от левых сертификатов |
| **PTR** | обратный: IP → имя (in-addr.arpa) | reverse DNS, репутация почты, разведка |
| **SRV** | сервис+порт для протокола | service discovery (SIP, LDAP, Kubernetes) |
| **DNSKEY/RRSIG/DS/NSEC** | подписи DNSSEC | целостность DNS (см. §7) |
| **ALIAS/ANAME** | «CNAME для корня зоны» (нестандартный) | у apex-домена CNAME нельзя — обходят так |

Практика на твоём стенде:
```bash
dig A     transfermarket.example.com +short   # твой IP
dig NS    example.com +short                   # кто авторитативен за зону
dig SOA   example.com                          # серийник + negative-cache TTL
dig CAA   example.com +short                   # разрешённые CA (может быть пусто — плохо)
dig TXT   example.com +short                   # SPF/верификации
dig -x    <твой_IP> +short                     # PTR (обратная запись)
```

Важное про **CNAME**: он не может стоять на apex-домене (голом `example.com`) и не
может сосуществовать с другими записями на том же имени. Поэтому корень домена
почти всегда A-запись, а `www` — часто CNAME на корень.

## 5. TTL и кеширование — где ломаются мозги (и деплои)

Каждая запись отдаётся с **TTL** (Time To Live) в секундах — «сколько можно верить
этому ответу, не переспрашивая». Резолверы кешируют ответ на TTL секунд.

Два вида кеша, оба кусаются при изменениях:

1. **Позитивный кеш.** Сменил IP A-записи, а старый TTL был 3600 — резолверы по
   всему миру ещё до часа отдают старый IP. Твой авторитативный сервер уже отдаёт
   новый, а клиенты видят старый. Это **не баг, это кеш.**

2. **Негативный кеш (negative caching).** Самый коварный. Если кто-то спросил имя
   **до** того, как ты создал запись, резолвер закешировал ответ `NXDOMAIN`
   («домена нет»). Время жизни этого «нет» берётся из **поля minimum в SOA-записи**
   зоны, а не из TTL самой записи (которой ещё нет). Ты уже добавил A-запись, а
   резолвер N минут уверенно говорит «нет такого домена».

**Правило миграции (классический вопрос на собесе):** перед плановой сменой IP
**заранее снижают TTL** (например до 300 сек), ждут, пока по миру истечёт старый
большой TTL, и только потом меняют запись. Тогда переключение занимает минуты, а
не часы. Снижать TTL в момент переезда бесполезно — старый TTL уже разошёлся по
кешам.

Диагностика «почему не переключается»:
```bash
dig transfermarket.example.com @1.1.1.1        # что видит публичный резолвер (+ остаток TTL)
dig transfermarket.example.com @<твой_авторитативный_NS>   # что отдаёт истина напрямую
```
Если authoritative отдаёт правильно, а `1.1.1.1` — по-старому → это кеш, ждём TTL.

## 6. Инструменты диагностики

```bash
dig example.com                 # полный ответ (секции QUESTION/ANSWER/AUTHORITY)
dig example.com +short          # только значение — для скриптов
dig +trace example.com          # обход от корня, МИНУЯ кеши резолвера
dig A example.com @8.8.8.8      # спросить конкретный резолвер
dig +noall +answer example.com  # только секция ответа
dig +dnssec example.com         # запросить DNSSEC-подписи (RRSIG)
host example.com                 # человекочитаемо
nslookup example.com             # старый, но привычный

# в ответе смотри на: статус (NOERROR / NXDOMAIN / SERVFAIL), флаги (aa=authoritative,
# ad=DNSSEC-проверен), TTL рядом с каждой записью.
```

Понимание кодов ответа — половина отладки:
- `NOERROR` + пустой ANSWER — имя есть, но записи такого типа нет.
- `NXDOMAIN` — имени не существует (кешируется негативно!).
- `SERVFAIL` — резолвер не смог получить ответ (часто = проблема DNSSEC или мёртвый NS).
- `REFUSED` — сервер отказал (например, запрещён рекурсивный запрос извне — это правильно).

## 7. DNSSEC — целостность DNS

**Проблема:** классический DNS ходит по UDP без аутентификации. Ответ можно
подделать — если атакующий успеет ответить раньше настоящего сервера или отравит
кеш резолвера, клиент поедет на вражеский IP, ничего не заметив.

**Cache poisoning (отравление кеша), атака Камински (2008):** атакующий засыпает
резолвер поддельными ответами с угаданным Query ID, пока один не «приклеится» в
кеш. Митигация тогда — рандомизация Query ID + порта источника. Полное решение —
DNSSEC.

**DNSSEC** добавляет криптоподписи к записям:
- **RRSIG** — подпись набора записей.
- **DNSKEY** — публичный ключ зоны, которым проверяется RRSIG.
- **DS** (Delegation Signer) — хеш ключа дочерней зоны, лежит в *родительской* зоне.
  Так строится **цепочка доверия**: корень подписывает `.com`, `.com` подписывает
  `example.com`. Корневой ключ — «якорь доверия», зашит в резолверы.
- **NSEC/NSEC3** — доказательство *отсутствия* записи (чтобы «нет» тоже нельзя было
  подделать). NSEC3 хеширует имена, чтобы нельзя было «прогуляться» по зоне и
  вычитать все имена (zone walking).

Что важно понимать для DevSecOps:
- DNSSEC защищает **целостность и подлинность**, но **НЕ конфиденциальность** —
  запросы всё ещё видны в открытом виде (для приватности нужен DoH/DoT, §11).
- Флаг `ad` (Authenticated Data) в ответе валидирующего резолвера = подпись
  проверена.
- Сломанный DNSSEC (просроченные подписи, рассинхрон ключей при ротации) =
  массовый `SERVFAIL` и «сайт лёг для части пользователей». DNSSEC — мощно, но
  требует аккуратной эксплуатации ключей.

```bash
dig +dnssec example.com          # увидишь RRSIG рядом с записями, если DNSSEC включён
dig DS example.com +short        # хеш ключа в родительской зоне
```

## 8. DNS как поверхность атаки и разведки (offensive-взгляд)

Чтобы защищать — надо понимать, как ломают. DNS — это первое, что смотрит атакующий.

### 8.1 Subdomain enumeration (перечисление поддоменов)
Атакующий собирает карту твоей инфраструктуры через DNS: `api.`, `dev.`, `staging.`,
`vpn.`, `grafana.`, `jenkins.`… Источники: брутфорс по словарю, **Certificate
Transparency логи** (каждый выпущенный TLS-сертификат публичен → все домены, на
которые ты выпускал серты, видны любому на `crt.sh`), пассивный DNS.
**Вывод для тебя:** каждый поддомен, который ты поднимаешь (тот же `quake.`),
становится публично известен. Не рассчитывай на «security through obscurity».

### 8.2 Zone transfer (AXFR) — классическая мисконфигурация
Механизм репликации зоны между NS-серверами (master → slave). Если авторитативный
сервер по ошибке разрешает AXFR кому угодно — атакующий одной командой скачивает
**всю зону целиком** (все имена, все IP, вся внутренняя карта):
```bash
dig AXFR example.com @ns1.example.com     # должно быть REFUSED/пусто с чужого хоста!
```
Это находка №1 в любом пентесте DNS. Проверь свой NS — AXFR должен быть разрешён
только доверенным slave-серверам (по IP + TSIG-ключу).

### 8.3 Subdomain takeover (захват поддомена) — топ-тема DevSecOps
Сценарий: у тебя есть `CNAME shop.example.com → myshop.herokuapp.com`. Потом ты
удалил приложение на Heroku, но **забыл убрать CNAME**. Запись «висит» (dangling),
указывая на освободившийся ресурс. Атакующий регистрирует `myshop.herokuapp.com`
на себя — и теперь **его контент отдаётся с твоего доверенного домена**
`shop.example.com`: фишинг, кража cookie (если домен общий), обход CSP.
**Профилактика:** при выводе сервиса из эксплуатации — сначала удаляй DNS-запись,
потом ресурс. Регулярно сканируй зону на dangling-записи.

### 8.4 DNS tunneling / exfiltration (C2 и утечка через DNS)
DNS-запросы почти нигде не блокируются (иначе интернет не работает). Атакующие
этим пользуются: кодируют украденные данные в имена поддоменов
(`ZXhmaWx0cmF0ZWQtZGF0YQ.attacker.com`) и «сливают» их запросами на свой
авторитативный сервер, а ответы используют как канал управления (C2). Легитимного
DNS-трафика много → аномалию трудно заметить.
**Защита:** мониторинг DNS-логов на аномалии (длинные/энтропийные имена, объём
запросов на один домен, редкие типы вроде `TXT`/`NULL`), DNS-firewall.

### 8.5 DNS amplification (усиление) — DDoS
DNS по UDP → можно **подделать source IP** (жертвы). Атакующий шлёт маленький
запрос (`ANY`/`DNSKEY`) с адресом жертвы на открытые резолверы; те отвечают
**большим** ответом жертве. Коэффициент усиления — десятки раз. Тысячи открытых
резолверов → заваливают жертву.
**Защита:** не держи **открытый рекурсивный резолвер** в интернете (рекурсию —
только для своих сетей); Response Rate Limiting (RRL) на авторитативных серверах;
на сети — anti-spoofing (BCP38).

### 8.6 DNS rebinding — обход Same-Origin Policy к внутренней сети
Атакующий домен с TTL=0. Браузер жертвы заходит на `evil.com` → сначала резолвится
в IP атакующего (грузится JS), затем TTL истекает, и `evil.com` пере-резолвится в
**внутренний IP** (`127.0.0.1`, `192.168.x.x`). JS в браузере теперь обращается к
внутренним сервисам «от имени того же origin», обходя SOP — так лезут к роутерам,
admin-панелям, метадата-сервисам облака.
**Защита:** приложения проверяют заголовок `Host` (whitelist), не доверяют
внутреннему трафику по факту сети; резолверы фильтруют приватные IP в ответах
внешних доменов (DNS rebinding protection в Pi-hole/dnsmasq).

## 9. DNS и сертификаты (TLS) — прямая связка с твоим nginx

Когда повесишь HTTPS на `transfermarket.` и `quake.`, DNS участвует дважды:

### 9.1 SNI (Server Name Indication)
На 443 порту заголовок `Host` зашифрован внутри TLS. Как nginx поймёт, чей
сертификат отдавать, ещё *до* расшифровки? Браузер сообщает имя домена **открытым
текстом на этапе TLS-рукопожатия** — это SNI. По нему nginx выбирает нужный
`server`-блок и сертификат. (На 80 порту тот же выбор делается по `Host` из HTTP.)
> Нюанс приватности: классический SNI виден в сети → провайдер знает, на какой
> домен ты идёшь, даже по HTTPS. Решение — **ECH (Encrypted Client Hello)**.

### 9.2 ACME DNS-01 challenge (Let's Encrypt)
Чтобы выпустить сертификат, надо доказать, что домен твой. Способ **DNS-01**: CA
просит создать TXT-запись `_acme-challenge.transfermarket.example.com` с
конкретным токеном. Ты (или certbot) её создаёшь, CA проверяет через DNS — и
выдаёт серт. Это единственный способ получить **wildcard-сертификат**
(`*.example.com`) и выпускать серты для сервисов без публичного HTTP.
```bash
dig TXT _acme-challenge.example.com +short   # так CA проверяет владение
```

### 9.3 CAA (Certificate Authority Authorization)
TXT-подобная запись, которая говорит: «сертификаты для моего домена может
выпускать только вот этот CA (например `letsencrypt.org`)». Без CAA **любой** CA
может выпустить серт на твой домен (если его обманут или он скомпрометирован) — и
это будет валидный серт для MITM. CAA сужает это до одного-двух доверенных CA.
```bash
dig CAA example.com +short
# пример значения: 0 issue "letsencrypt.org"
```
**Обязательный DevSecOps-хардненинг:** поставь CAA. Это одна запись, которая
закрывает целый класс атак с левыми сертификатами.

## 10. Почта = DNS (SPF / DKIM / DMARC)

Даже если ты не «про почту», это классические DevSecOps-записи в TXT, и их
спрашивают:

- **SPF** (`TXT`): список серверов, которым разрешено слать почту от твоего домена.
  `v=spf1 include:_spf.google.com -all` — «только Google, остальное отвергать».
  Защита от подделки отправителя.
- **DKIM** (`TXT`): цифровая подпись писем публичным ключом в DNS. Получатель
  проверяет, что письмо не подменили и оно реально от твоего домена.
- **DMARC** (`TXT` на `_dmarc.`): политика «что делать, если SPF/DKIM не прошли»
  (`p=reject` — отвергать) + куда слать отчёты. Связывает SPF и DKIM воедино.

Без этих трёх записей любой может рассылать фишинг «от твоего домена». Это часть
базовой гигиены безопасности любого домена.

## 11. Приватность транспорта: DoH и DoT

Классический DNS (порт 53, UDP) — открытый текст. Любой на пути видит, какие
домены ты резолвишь (даже при HTTPS-контенте). Шифрованные варианты:

- **DoT — DNS over TLS** (порт **853**): DNS в TLS-туннеле. Отдельный порт → легко
  заблокировать/заметить на файрволе.
- **DoH — DNS over HTTPS** (порт **443**): DNS внутри обычного HTTPS. Сливается с
  веб-трафиком → трудно отличить и заблокировать.

**Двойственность для DevSecOps:**
- **Плюс:** приватность пользователей, защита от подмены на пути.
- **Минус:** DoH **обходит корпоративные DNS-фильтры** (Pi-hole, RPZ, блокировки
  вредоносных доменов) — малварь тоже умеет ходить по DoH мимо твоего мониторинга.
  Поэтому в защищённых сетях DoH к внешним резолверам часто запрещают, а свой
  резолвер делают DoH/DoT.

Помни: **DoH/DoT шифруют транспорт, DNSSEC подтверждает подлинность** — это
ортогональные вещи, а не замена друг другу. В идеале нужны оба.

## 12. DNS в Kubernetes (пригодится на следующих фазах роадмапа)

Внутри кластера DNS — это как поды находят друг друга. Разбираться придётся, поэтому
закладываю базу:

- **CoreDNS** — DNS-сервер кластера (под в `kube-system`). Резолвит внутренние имена.
- **Формат имени сервиса:** `<service>.<namespace>.svc.cluster.local`. Под в
  namespace `default` может звать `transfermarket.staging.svc.cluster.local`.
- **ClusterIP** сервиса — виртуальный IP, за которым kube-proxy балансирует поды.
  DNS отдаёт именно его.
- **Headless service** (`clusterIP: None`) — DNS отдаёт IP всех подов напрямую
  (нужно для StatefulSet, баз данных).
- **`ndots:5` — знаменитая ловушка производительности.** По умолчанию в поде
  `/etc/resolv.conf` содержит `options ndots:5`: если в имени меньше 5 точек, k8s
  сначала пробует его во всех search-доменах (`.svc.cluster.local`,
  `.cluster.local`, …) и только потом как есть. Итог: запрос к внешнему
  `api.stripe.com` порождает 4–5 лишних DNS-запросов → латентность и нагрузка на
  CoreDNS. Лечится указанием FQDN с точкой на конце (`api.stripe.com.`) или
  тюнингом `dnsConfig`.

**Security-грани в k8s DNS:**
- CoreDNS-логи — источник для детекта аномалий (DNS-туннелирование из скомпро­
  метированного пода).
- NetworkPolicy обычно должна разрешать DNS (UDP/TCP 53 к CoreDNS) — забыл → всё
  «необъяснимо» перестаёт резолвиться.
- DNS-spoofing внутри кластера при слабой сетевой изоляции.

## 13. Оборонительный DNS в инфраструктуре

- **RPZ (Response Policy Zones)** — «файрвол для DNS»: резолвер подменяет ответы
  для известных вредоносных доменов (C2, фишинг, малварь) на «никуда». Фиды
  угроз обновляются как блок-листы.
- **Pi-hole / AdGuard** — тот же принцип на уровне SOHO/сети: блок рекламы и
  трекеров через подмену DNS.
- **Split-horizon (split-brain) DNS** — один домен отдаёт **разные** ответы
  изнутри и снаружи: снаружи `app.example.com` → публичный балансировщик, изнутри
  → приватный IP. Разделяет внутреннюю и внешнюю карту сети.
- **DNS-логирование и мониторинг** — query-логи резолвера/CoreDNS в SIEM; алерты
  на аномалии (см. §8.4).
- **Rate limiting (RRL)** на авторитативных серверах — против amplification.
- **Мониторинг делегирования и сертификатов** — следить за Certificate
  Transparency (кто выпускает серты на твои домены) и за изменениями NS/DS.

## 14. Практика на твоём стенде (сделай прямо сейчас)

```bash
# 1. Полный путь резолва твоего приложения от корня
dig +trace transfermarket.<твой-домен>

# 2. Сравни истину и кеш
dig transfermarket.<твой-домен> @<твой-авторитативный-NS>
dig transfermarket.<твой-домен> @1.1.1.1

# 3. Проверь, что оба поддомена (transfermarket и quake) резолвятся в один IP
dig +short transfermarket.<твой-домен>
dig +short quake.<твой-домен>
#   → один IP, а nginx разводит по server_name (Host) — это ты уже построил

# 4. Убедись, что AXFR закрыт (должно быть НЕ "успешно скачал всю зону")
dig AXFR <твой-домен> @<твой-NS>

# 5. Есть ли CAA? (скорее всего нет — это твоя следующая задача по хардненингу)
dig CAA <твой-домен> +short

# 6. Виртуальный хостинг без DNS — проверка Host-роутинга напрямую
curl -H "Host: transfermarket.<твой-домен>" http://<IP-сервера>/
curl -H "Host: quake.<твой-домен>" http://<IP-сервера>/
```

Мини-задание по хардненингу (реально полезно твоему стенду):
1. Поставь **CAA**-запись, разрешив только своего CA (Let's Encrypt).
2. Проверь, что **AXFR** закрыт для чужих.
3. Убедись, что на сервере **нет открытого рекурсивного резолвера** наружу
   (`dig google.com @<твой-IP>` с чужой машины должен быть REFUSED).

## 15. Вопросы для самопроверки

Ответишь без гугла — тема закрыта:

1. Чем отличается рекурсивный запрос от итеративного и кто какой делает?
2. Почему нельзя поставить CNAME на apex-домен (`example.com`)?
3. Откуда берётся TTL негативного (NXDOMAIN) кеша — почему не из самой записи?
4. Почему перед миграцией сервера TTL снижают **заранее**, а не в момент переезда?
5. Что защищает DNSSEC, а что — нет? Почему DoH его не заменяет?
6. Как работает subdomain takeover и на каком шаге вывода сервиса его предотвращают?
7. Зачем нужна CAA-запись, если уже есть валидация домена при выпуске серта?
8. Почему открытый рекурсивный резолвер — это подарок для DDoS-амплификации?
9. Что такое `ndots:5` в Kubernetes и почему из-за него «тормозит» резолв внешних API?
10. Как одной командой проверить, не разрешён ли на твоём NS зонный трансфер кому попало?
